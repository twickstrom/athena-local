# Project Instructions

## Purpose

Build a lightweight, open-source, AWS Athena API-compatible local development server backed by Trino.

Applications must communicate with the service using the real AWS SDK v3 `AthenaClient` and standard Athena commands. The project targets application-integration parity, not complete AWS infrastructure emulation.

## Runtime and Tooling

- Use Bun exclusively for JavaScript and TypeScript execution.
- Do not introduce Node-only native modules.
- Do not use DuckDB.
- Support both Apple `container` and Docker through a shared runtime abstraction.
- Do not require Docker Compose.
- Keep OCI images and service configuration portable where practical.
- Use TypeScript with strict type checking.
- Prefer built-in Bun capabilities over unnecessary dependencies.

Use these Bun-native APIs where appropriate:

- `Bun.serve()`
- `bun:sqlite`
- `Bun.S3Client`
- `Bun.spawn()`
- `bun:test`
- native `fetch()`
- `Bun.file()`

## Proposed Architecture

The local environment consists of:

- A Bun-based Athena-compatible API facade
- Trino as the query execution engine
- MinIO as the default local S3-compatible object store
- Optional AWS S3 storage backend for explicitly configured development prefixes
- Hive Metastore for catalog metadata
- PostgreSQL for Hive Metastore persistence
- SQLite for local Athena query-execution state
- Apple `container` and Docker adapters behind a shared typed runtime interface

The application must use:

- `@aws-sdk/client-athena`
- `@aws-sdk/client-s3`

Only endpoint, credentials, region, and environment configuration should differ between local and production environments.

## Initial Supported Athena Operations

Implement application-level compatibility for:

- `StartQueryExecution`
- `GetQueryExecution`
- `GetQueryResults`
- `StopQueryExecution`

Support the associated behavior:

- Query execution IDs
- `ClientRequestToken` idempotency
- `QUEUED`
- `RUNNING`
- `SUCCEEDED`
- `FAILED`
- `CANCELLED`
- Polling
- Cancellation
- Athena-compatible response shapes
- Athena-compatible error shapes
- Result pagination
- `MaxResults`
- `NextToken`
- `ResultConfiguration.OutputLocation`
- CSV result materialization
- MinIO result output
- Explicitly configured AWS S3 result output
- Query metadata and basic statistics
- Restart-aware persisted execution state

## Protocol Requirements

- Accept requests generated by the real AWS SDK v3.
- Implement the AWS JSON protocol used by Athena.
- Route operations using the AWS target header.
- Do not require application-specific HTTP clients.
- Signature verification is not required for the initial local implementation.
- Signed SDK requests must be accepted.
- Integration tests must invoke the service through `AthenaClient`, not only through direct HTTP requests.

## S3 Requirements

Application code should continue using `@aws-sdk/client-s3`.

Use `Bun.S3Client` only inside local infrastructure code where it is an implementation detail, including:

- Athena result materialization
- Fixture seeding
- Test assertions
- Local maintenance tooling

Do not build a custom S3-compatible server. Use MinIO for local S3-compatible storage.

Real AWS S3 support must be opt-in and safe by default:

- Require explicit bucket and prefix configuration.
- Reject empty destructive prefixes.
- Reject root-level bucket deletion behavior.
- Keep local reset separate from remote S3 cleanup.
- Never log credentials or sensitive signed URLs.

## Trino Requirements

- Communicate with Trino using native `fetch()`.
- Implement the documented Trino HTTP statement protocol directly.
- Submit SQL through `/v1/statement`.
- Follow `nextUri` until completion.
- Support cancellation through the Trino protocol.
- Persist enough execution state to service independent Athena polling requests.
- Map Trino states and errors into Athena-compatible states and errors.

## State Requirements

Use `bun:sqlite` for local query-execution state.

- Enable WAL mode where appropriate.
- Use migrations or an explicit schema version.
- Use prepared statements.
- Make query submission idempotent for repeated client request tokens.
- Do not keep authoritative query state only in process memory.
- Design restart behavior explicitly.

## Container Runtime Requirements

Support both:

- Apple `container`
- Docker Engine or Docker Desktop where compatible

Runtime selection precedence:

1. CLI flag
2. Environment variable
3. Saved local configuration
4. Automatic detection
5. Interactive prompt when stdin and stdout are attached to a TTY

Never prompt in CI or noninteractive execution.

## Testing Requirements

Use `bun:test`.

Required test layers:

1. Unit tests for state transitions, pagination, serialization, and error mapping
2. Protocol tests for AWS JSON request and response handling
3. SQLite tests
4. Trino client tests, mostly against deterministic fake protocol servers
5. MinIO integration tests
6. Container runtime adapter tests
7. End-to-end tests using the real AWS SDK v3
8. Opt-in AWS S3 and Athena contract tests
9. Regression tests for all discovered compatibility issues

The primary proof of compatibility is an integration test that constructs `AthenaClient` with:

- A localhost endpoint
- Region `us-east-1`
- Local access-key credentials

Do not claim a feature is supported unless it is covered by an AWS SDK integration test.

## Explicit Non-Goals

Do not expand the initial project into a general AWS emulator.

The initial scope excludes:

- Full Athena API coverage
- Full Glue API compatibility
- IAM policy evaluation
- Lake Formation
- KMS behavior
- Glue crawlers
- Athena billing
- Exact bytes-scanned parity
- Federated Athena connectors
- Complete workgroup enforcement
- Every AWS throttling behavior
- Complete S3 emulation
- Exact parity for every Athena engine edge case

Document unsupported behavior clearly rather than silently approximating it.

## Development Method

- Read the relevant architecture documents before changing code.
- Plan work before implementation.
- Work in small, independently testable milestones.
- Do not implement future milestones early.
- Avoid speculative abstractions.
- Keep public interfaces minimal.
- Prefer explicit behavior over hidden magic.
- Document important parity differences.
- Add tests with every behavior change.
- Run all relevant checks before declaring work complete.

## Dependency Policy

- Prefer Bun-native and standard Web APIs.
- Add dependencies only when they materially reduce complexity or risk.
- Avoid dependencies requiring Node-specific native addons.
- Pin OCI image versions.
- Do not use floating `latest` image tags.
- Keep production dependencies separate from development and test dependencies.

## Code Quality

- Enable strict TypeScript.
- Avoid `any`; use `unknown` and validate external input.
- Validate all environment configuration at startup.
- Keep AWS protocol types separate from internal domain models.
- Keep Trino response types separate from Athena response types.
- Use exhaustive state handling.
- Return structured errors.
- Never expose secrets in logs.
- Use deterministic IDs and clocks in tests where practical.

## Open-Source Requirements

- Keep company-specific assumptions out of the project.
- Use generic examples and fixtures.
- Include a clear AWS trademark and affiliation disclaimer.
- Do not imply endorsement by Amazon Web Services.
- Use the MIT License unless a concrete project-specific reason is documented for changing it.
- Document supported operations and compatibility limits prominently.
